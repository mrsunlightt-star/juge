## 一、本轮修复完成

### 1. 小组件 Provider 的公开广播入口可被伪造（安全）

**问题**：`ReminderWidgetProvider.onReceive` 处理自定义 action
`miui.appwidget.action.APPWIDGET_UPDATE` 时，直接采用广播里自带的
`EXTRA_APPWIDGET_IDS` 触发渲染。该 receiver 必须 `exported=true` 才能收到系统的
`APPWIDGET_UPDATE`，因此自定义 action 同样对全设备可见——任意应用都能伪造广播，
让本应用做无意义的读库 + 位图渲染（配合单线程渲染队列可放大为 CPU 占用）。

**修复**（`ReminderWidgetProvider.kt`）：广播里的 ID 只作为「候选」，必须与
`getAllAppWidgetIds()`（系统实际登记在本应用名下的组件）取交集，并限制单次最多
64 个 ID。

### 2. 组件删除后留下孤儿配置行，且配置行会被复用串味

**问题**：`DbHelper.deleteWidgetConfig` 定义了却无任何调用方；组件删除时只清
SharedPreferences 绑定。自动创建的 `微件 <id>` 配置行只增不减。另外
`bindReminderToWidget` 在未绑定时无条件 `insert`，每次「把金句推到桌面」都可能新增一行。

**修复**：
- 新增 `data/WidgetConfigBinding.kt`，把「哪些行可回收 / 可复用」抽成纯函数，
  并加 JVM 单测（`WidgetConfigBindingTest`，6 个用例）；
- `onDeleted` 后异步回收孤儿行；
- `bindReminderToWidget` 优先复用无绑定的自动配置行。

**安全边界**：回收与复用**只碰自动创建的行**（名称前缀 `微件 `），用户手动创建的
与旧数据迁移导入的行一律不动，避免误删内容。这一点有专门的测试用例锁定。

### 3. 服务端 PRO 状态不回灌：激活标记可能长期残留（双向同步）

**问题**：`MainActivity` / `QuickAdjustActivity` 只在服务端说「已购」时写入本地激活，
服务端说「不是 PRO」时不动。盗号、共享账号、退款等场景下本地激活会永久残留。

**修复**：`AccountSync.refresh` 改为返回三态结论
（`NotLoggedIn` / `Unavailable` / `ServerSays(pro)`）。只有
`ServerSays(pro = false)` 才允许撤销，且**仅撤销由账号授予的激活**
（`activationRecord().payMethod == PAY_METHOD_ACCOUNT`）。两个例外必须保留：

- 本机直接购买（`payMethod = 支付宝`）：钱是这台设备付的，与账号状态无关；
- 开发开关（`payMethod = 开发开关`）：保留调试能力。

未登录、请求失败（网络抖动、服务端 5xx）一律保持本地状态不变——否则断网就掉 PRO。

### 4. 无证书固定（pinning）

**修复**（`res/xml/network_security_config.xml`）：为 `puretxt.cn` 增加 `pin-set`。

- 只 pin **链上 CA**（Let's Encrypt 中间 CA `YR2` + 根 `ISRG Root YR`），
  **不 pin 叶子证书**——叶子 90 天一续期，pin 叶子等于每次自动续期都把用户挡在门外；
- 设置 `expiration="2027-12-31"`：到期后系统会忽略 pin-set 回落到普通校验，
  这是「忘了更新也不至于锁死」的保险；
- 文件内写明了取哈希的命令与更新时机（LE 换中间 CA 或站点换 CA）。

**已在 release 包内实测**：`aapt2 dump xmltree` 可见 `pin-set` 与两个 `pin` 节点。

### 5. `/api/alipay/notify` 无频次限制

**问题**：`create` / `query` 都接了 `PayApiThrottle`，唯一接受公网匿名 POST 的
`notify` 反而是裸的，每次都要跑一次 RSA 验签，是现成的 CPU 放大点。

**修复**：`notify` 接入同一套节流，限额取 300 次/分钟/IP（只为防洪，不影响正常投递）。
被限流时返回 `failure` 而不是 429：支付宝对非 `success` 的响应会按官方节奏重投
（最长 25 小时），正常通知最坏只是延迟到账，不会丢单。真正的防伪仍靠验签。

### 6. 订单状态变更存在并发窗口（资金安全）

**问题**：`PayOrderService.markPaid` 是「先读状态 → 判断 → 改状态」。支付宝会对同一笔
订单并发重投通知，两个事务都会读到 `CREATED`，从而重复发货。原实现靠
「恰好幂等」兜底而不是靠约束。

**修复**：改成数据库层 compare-and-set——`PayOrderRepository.markPaidIfCreated`
用带 `status = CREATED` 条件的 `UPDATE`，只有 affected rows = 1 的那一次才继续
开通 PRO；返回 0 直接按 `AlreadyPaid` 幂等短路。

**测试**：`PayOrderServiceTest.并发重复通知也只有一次真正落单` —— 4 线程并发，
断言恰好 1 个 `Marked`、其余全部 `AlreadyPaid`。

### 7. R8 可能破坏枚举字符串协议（release 风险）

**问题**：`WidgetStyle` 用 `Enum.name()` 序列化、`valueOf()` 反序列化
（`safeEnum` / `fromJsonString`）。R8 的 enum unboxing 会移除 `name()` 字符串，
编译期无任何提示，但用户桌面上已保存的组件样式会全部读不回来。

**修复**：`proguard-rules.pro` 增加 `-keepclassmembers enum * { values(); valueOf(...); }`。

**已在 release 包内实测**：
- `mapping.txt` 中 `WidgetShape.valueOf` / `WidgetFont.valueOf` / `ImageScaleMode.valueOf` 均保留；
- 资源收缩未误删插画：`aapt2 dump resources` 可见 64 个 drawable，抽查
  `deepsea_whale` / `lotus_frame` / `pixel_retro` / `winter_frame` 均在；
- `assets/fonts/` 7 个字体文件都在包内。

### 11. 首启隐私弹窗只讲「纯本地」，未披露账号与支付（合规）

**问题**：`PrivacyPolicyDialog` 是取得同意前唯一的告知界面，原文只说了
「纯本地小部件应用 + 相册选择」，但应用实际还有两条会把信息送出设备的路径：

交易号与买家标识用于对账）。政策全文里写了账号与支付，首启弹窗却只讲本地——

**修复**（`app/src/main/java/com/juge/app/ui/legal/PrivacyPolicyDialog.kt`）：

**背景**：`CardTextRenderer` 会在正文左上/右下画一对低透明度的艺术双引号
（`showQuoteMark = true` 时生效），21 个内置预设开着。用户决定所有组件风格
都不再出现这对引号，只保留文字本身。

**修复**：

  `QUOTE_ALPHA` 两个只服务它的常量；
- `data/WidgetStyle.kt`：移除 `showQuoteMark` 字段、JSON 读写、21 处预设赋值，
  以及 `isProPreset` 旧数据兜底里的字段比对。老数据里的同名 key 会被 `optBoolean`

- `WidgetCanvasRenderer.THUMB_DISK_VERSION` 1 → 2：缩略图磁盘缓存按「版本号 +
  presetId + 尺寸」寻址，改绘制逻辑不 bump 就会继续贴旧图（真机上第一次验证

  重生成前已逐场景 `diff` 语义摘要，**语义零差异**，变化只在像素（引号消失）。

**顺带修正**：`docs/component-styles-overview.md` 的样式字段表删掉 `showQuoteMark` 一行。

## 二、复核后撤回或更正的判断

### 1. 「官网源码不在版本控制里」——**判断有误，已撤回**

实际情况：`juge-website/` 是一个**独立的 git 仓库**，有远程备份
（`ssh://root@1.15.174.33/www/repo/puretxt-site.git`），工作区干净，
当前 HEAD 为 `641167b`（2026-10-02）。它只是被主仓库 `.gitignore` 排除，
并非不受版本控制。**不做改动**。

残留的真实风险（记录，未处理）：
- 主仓库没有 pin 网站版本，无法回答「这个 APK 对应哪一版官网」；
- 网站的裸仓库与站点部署在同一台服务器上，服务器整体丢失时会同时丢掉两者。

### 2. 「内存靠 GC 兜底」——**降级**

核对后：预览位图不进入任何静态缓存，离开组合即成为垃圾，属 GC 压力而非内存泄漏。
**有意不改为显式 `recycle()`**：位图可能仍在 `Image` 的绘制路径上，
过早回收会直接抛 `Canvas: trying to use a recycled bitmap` 崩溃，风险高于收益。
仅把缩略图 LruCache 上限从 64MB 收到 32MB 作为安全阀（实际用量约 6MB，
远达不到，纯粹是防 key 设计出错时的兜底）。

### 3. `!!` 断言——**只改真正有竞态风险的两处**

共 16 处 `!!`，其中 14 处位于同一个组合函数内对 Compose 状态的读写。
Compose 的状态读取在一次组合内是稳定的，这类 `!!` 实际不会 NPE，属写法问题而非缺陷；
为它们翻改 3000 行组合函数的风险大于收益。
已改的是两处**跨 lambda/挂起**的 `pendingCropUri!!`
（`MainActivity` / `QuickAdjustActivity`），改为局部快照判空。
