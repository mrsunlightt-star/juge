## 2. P0 — 阻断上线

### P0-1　生产环境所有 `/api/*` 返回 404，付费与账号链路当前完全不可用

**证据**（2026-11-14 实测）：

```
404  /api/auth/me          → nginx 404 HTML
404  /api/alipay/create    → nginx 404 HTML
404  /api/alipay/query     → nginx 404 HTML
404  /actuator/health      → nginx 404 HTML
000  https://puretxt.cn:8081/api/auth/me  → 连接被拒（端口未开放）
200  /                     → 网站正常
```

**影响面**：

1. **下单 100% 失败**。`ProPurchase.purchase()` → `createOrder()` 拿到空 JSON → `success=false` → `Outcome.Failed("下单失败")`。付费墙点下去必然报错，等于首发即「买不了」。
2. **换机找回 100% 失败**。`AccountSync.refresh()` 永远走 `Unavailable`。
3. **更隐蔽的一条**：`notifyUrl` 配的是 `https://puretxt.cn/api/alipay/notify`。若服务恢复但 nginx 仍缺 `/api/` 反代，支付宝异步通知会持续 404，订单永远停在 `CREATED`——用户付了钱、PRO 不开，只能人工对账。

**两种可能原因，需现场确认是哪一种**：

- Spring Boot 进程未部署 / 已停止（8081 不可达支持这一判断）；
- 进程在跑，但 nginx 缺 `location /api/ { proxy_pass http://127.0.0.1:8081; }`（网站 200、API 404 也支持这一判断）。

**建议**：发布前把「`curl` 四个端点」写进上线检查清单，而不是靠打开 App 试。四条命脉：

```bash
curl -o /dev/null -w "%{http_code}\n" https://puretxt.cn/api/auth/me          # 期望 401
curl -o /dev/null -w "%{http_code}\n" "https://puretxt.cn/api/alipay/query?outTradeNo=X"  # 期望 404 + JSON
curl -X POST https://puretxt.cn/api/alipay/notify -d "" -o /dev/null -w "%{http_code}\n"  # 期望 200 failure
```

## 3. P1 — 首发前应修

### P1-1　服务端故障被压成「下单失败」，且 HTTP 状态码被整体丢弃

**位置**：`app/src/main/java/com/juge/app/net/ServerClient.kt:58-62`

```kotlin
private fun readResponse(conn: HttpURLConnection): JSONObject {
    val stream = if (conn.responseCode in 200..299) conn.inputStream else conn.errorStream
    val text = stream?.bufferedReader()?.use { it.readText() }.orEmpty()
    return runCatching { JSONObject(text) }.getOrElse { JSONObject() }   // 状态码在这里丢失
}
```

`HttpURLConnection.responseCode` 被读了一次就扔掉，返回体只保留 `JSONObject`。后果是 **404（路由缺失）、502（后端挂了）、500（服务端 bug）、429（限流）四类完全不同的故障，在客户端压缩成同一个 `{}`**，最后统一显示成「下单失败」四个字。

线上真实表现会是：用户截图说「点了没反应」，而这条信息无法区分「我们的服务没起」和「用户的网断了」——正是 P0-1 这种问题最难被发现的原因。

**建议**（改动很小，收益很大）：让 `readResponse` 返回 `data class Response(val status: Int, val json: JSONObject)`，在 `AlipayPayApi` / `AccountApi` 里把 `status >= 500 || status == 404` 映射成独立文案「服务暂时不可用，请稍后重试或联系客服」。这不只是文案问题——它是把「运维故障」和「用户网络」分开的唯一手段。

### P1-2　`check(editor.commit())` 在系统恢复组件的路径上会直接崩溃

**位置**：`app/src/main/java/com/juge/app/ReminderWidgetProvider.kt:108`、`:318`

```kotlin
check(editor.commit()) { "Unable to restore widget bindings" }
```

`onRestored` 由系统在**换机/重装/备份恢复**时于主线程回调，这里 `check` 失败会抛 `IllegalStateException`，方法内无 try/catch → 未捕获 → 崩溃。

这个失败条件并不罕见：恢复场景下磁盘配额、`SharedPreferences` 写入失败、恢复期间存储受限都可能命中。**恰恰是「用户刚换新手机、第一次打开」这个最脆弱的时刻崩给他看。**

**建议**：改为 `if (!editor.commit()) { Timber.w(...); return }`。绑定恢复失败最多是组件丢配置（页面会显示兜底卡），远好于启动崩溃。`:318` 的 `bindIndependentConfig` 同理（虽然当前被上层 try/catch 兜住，但依赖上层是脆弱的）。

### P1-3　权限清单与隐私文案不一致（应用商店审核高风险）

**证据**：`app/src/main/AndroidManifest.xml:6` 只声明了 `INTERNET`。但 Release APK 实际申请了 4 个权限：

```
uses-permission: android.permission.INTERNET
uses-permission: android.permission.ACCESS_NETWORK_STATE     ← 支付宝 SDK 合并进来
uses-permission: android.permission.ACCESS_WIFI_STATE        ← 支付宝 SDK 合并进来
uses-permission: com.juge.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION  ← androidx
```

`app/build/outputs/logs/manifest-merger-release-report.txt:534-541` 明确记载这两条 `ADDED from com.alipay.sdk:alipaysdk-android:15.8.42`。

**为什么是 P1**：华为/小米/OPPO/vivo 的提审表单要求"权限清单"与实际 APK 逐条一致，并要求每个权限在隐私政策里说明用途。`ACCESS_WIFI_STATE` 属于审核员最容易追问的一类。当前 `LegalDocs.kt:123-130` 的第三方 SDK 清单只写了「支付宝支付 SDK / 用于拉起收银台、查支付结果、安全风控」，**没有逐条列出这两个权限及其用途**。

**建议**：在《隐私政策》第三方 SDK 段落补一行"该 SDK 会申请「查看网络连接状态」「查看 Wi-Fi 状态」权限，用于判断当前网络是否可用、避免在无网时反复重试"，并在各商店的权限说明栏照抄同一句话。不建议用 `tools:node="remove"` 强行删——可能导致 SDK 判断网络状态异常，反而拉起 H5 收银台。

### P1-4　价格存在两个真实来源，且没有任何一致性校验

**位置**：`app/.../pay/ProPurchase.kt:21`（`PRICE_TEXT = "￥3.99"`）vs `lkl-pay-server/src/main/resources/application.yml:26`（`amount-fen: 399`）

当前两边一致（这次专门核过），但**客户端展示的价格是写死的常量，服务端定价是另一份配置，中间没有任何自动校验**。项目历史上已经改过一次价（￥1.99 → ￥3.99，commit `b06bf7d`），说明这不是假想风险。

价格不一致在中国应用商店属于红线（"标价与实际支付金额不符"），而且很难在自测中发现——只有在真机点开收银台才能看见。

**建议**（二选一）：
- 下单接口在返回 `order_str` 的同时返回 `amount_yuan`，客户端用它渲染价格——彻底消灭第二来源；
- 或退一步：在 `ProPurchaseTest` 里加一条断言，直接读 `../lkl-pay-server/src/main/resources/application.yml` 的 `amount-fen`，与 `PRICE_TEXT` 对齐。测试跑在仓库内，路径可达，成本 10 行。

## 4. P2 — 可排期

### P2-1　没有 CI，239 个测试靠手动触发

仓库无 `.github/`、无任何 CI 配置。这套测试的质量很高（见 §5），但**只有在开发者想起来跑的时候才生效**。对单人项目，最低成本方案是 GitHub Actions 跑 `:app:testDebugUnitTest` + `testDebugUnitTest`（服务端 `mvnw test`），PR/推送即触发。

需要先解决一个障碍：`WidgetRenderBaselineTest` 依赖 Robolectric NATIVE 图形栈出像素指纹（`app/src/test/resources/widget-render-baseline.tsv`，150 行）。**Skia 在 macOS 与 Linux 上的抗锯齿/栅格化可能有细微差异**，在 CI 上大概率会红。建议 CI 只跑非渲染测试（约 40 个类），渲染基线保留在本地手动跑。

### P2-2　`MainAppScreen` 是典型的「上帝 Composable」

**位置**：`app/.../ui/main/MainAppScreen.kt`，**758 行、28 处 `remember`、11 处 `LaunchedEffect`、1 处 `DisposableEffect`**。

一个函数里同时承担：DB 加载、账号同步、PRO 撤销判定、支付找回、抽屉/翻页手势、预览高度计算、防抖落库、付费拦截、组件绑定。项目**完全没有 ViewModel 层**，业务规则直接写在 Composable 里，`DbHelper` 被 UI 直接调用。

这是全项目最大的可维护性负债——不是说现在会出错，而是**任何一处改动都要在 758 行里重新建立上下文**。建议下一次重构时按「账号与 PRO」「组件与样式编辑」「文库管理」三条线抽 ViewModel，`MainAppScreen` 只剩布局与转发。

顺带一个具体缺陷：`persistJob`（`:351`）是 `remember` 而非 `rememberSaveable`，屏幕旋转后 `LaunchedEffect(selectedWidgetId)`（`:363`）里的 `persistJob?.join()` 恒为 null，**"等防抖落库再读库"的保护在旋转这一下失效**，可能读到 400ms 前的旧值覆盖用户刚输入的草稿。

### P2-3　依赖版本"新旧混装"

`gradle/libs.versions.toml`：Compose BOM `2026.02.01` + Kotlin `2.2.10` + AGP `9.2.1`，但 `core-ktx 1.10.1`、`lifecycle-runtime-ktx 2.6.1`、`activity-compose 1.8.0` —— **这三个是 2023 年的版本**。

佐证：`MainAppScreen.kt:218` 用了已废弃的 `androidx.compose.ui.platform.LocalLifecycleOwner`，编译警告明确提示"已迁移到 lifecycle-runtime-compose"——正因为没引 `lifecycle-runtime-compose`，只能用旧入口。Lint 也报了 4 条 `NewerVersionAvailable`。

建议把 core/lifecycle/activity 三件套一并升到当前稳定版后再发版。现在能编译通过，但 Compose 2026 与 lifecycle 2.6 的协作是"碰巧成立"。

### P2-4　`targetSdk = 35` 落后 `compileSdk = 37`

`app/build.gradle.kts:15,29`。Lint 已报 `OldTargetApi`。需要按目标商店逐一确认：2026 年下半年，主流商店的 targetSdk 门槛可能已抬到 36。这不是代码问题，是上架资料问题，但**卡在审核最后一步才发现会很难受**，建议提前查五家商店当时的公告。

### P2-5　线上崩溃无感知

全项目未接入任何崩溃上报。这在隐私上是加分的（隐私政策明确"未接入广告、统计 SDK"），代价是**线上崩溃只能靠用户投诉发现**。

对于一个 ¥3.99 买断、用户量不大的产品，这个取舍可以接受，但要有配套：至少在 `JugeApplication` 里装一个 `Thread.setDefaultUncaughtExceptionHandler`，把堆栈写到 `filesDir/crash/`，在「我的」页提供一个"导出诊断信息"入口。不联网、不违反隐私政策，但用户反馈时能拿到真东西。

### P2-6　服务端是「单实例 + H2 文件库 + ddl-auto: update + 空口令」

**位置**：`lkl-pay-server/src/main/resources/application.yml:4-15`

```yaml
url: "jdbc:h2:file:${PAY_DB_PATH:./data/paydb};DB_CLOSE_DELAY=-1"
username: sa
password: ""
ddl-auto: update
```

当前 8081 端口不可达（已被安全组挡住），所以**现实风险低**；但这是一条靠部署纪律守住的红线——任何人一旦放开 8081，就等于把订单库（含 `buyer_logon_id`）暴露在公网。

另外 `ddl-auto: update` 意味着表结构随代码自动漂移，没有 Flyway 版本记录。在这个体量下可接受，但**一旦某次改字段改错，没有回滚依据**。建议至少每月跑一次 `scripts/backup-db.sh` 并把 `paydb.mv.db` 拉回本地留存。

### P2-7　缩略图缓存的注释与实现不符（会误导后续维护）

**位置**：`app/.../WidgetCanvasRenderer.kt:133-135` vs `:235-237`

实现只覆写了 `sizeOf`：

```kotlin
private val thumbnailCache = object : LruCache<String, Bitmap>(32 * 1024 * 1024) {
    override fun sizeOf(key: String, value: Bitmap): Int = value.byteCount
}
```

注释却写「**关闭了 LruCache 的条目回收**（`entryRemoved=false`）：条目只增不减、不会被淘汰」，并以此为依据「直接返回缓存原图、不做 copy()」。

事实是：**淘汰照常发生在 32MB**。当前不会崩（LruCache 淘汰只丢引用、不 recycle 位图，调用方手里的引用仍有效），但这个注释把一条**错误的前提**写成了设计依据。哪天有人顺着这条注释去加"淘汰时 recycle"，滚动列表就会拿到已回收位图并崩溃。

建议注释改成实话：「容量 32MB 远大于实际用量（约 2MB），实践中不触发淘汰；即便触发也只是丢引用，不 recycle，调用方持有的位图仍然有效」。

### P2-8　裁剪异常路径不回收中间位图

**位置**：`app/.../CropImageHelper.kt:258-277`

```kotlin
val croppedBitmap = Bitmap.createBitmap(targetWidth, targetHeight, ARGB_8888)
...
FileOutputStream(file).use { fos -> croppedBitmap.compress(...) ; fos.flush() }
croppedBitmap.recycle()          // ← compress / IO 抛异常时走不到这里
```

`cropTargetForWidget` 的输出上限是 4096×4096（`MAX_CROP_OUTPUT_DIMENSION`），单张最大 64MB 原生内存。异常时不回收，连续重试几次足以 OOM。建议改成 `try { ... } finally { if (!croppedBitmap.isRecycled) croppedBitmap.recycle() }`。

### P2-9　缩放组件时渲染任务会在单线程队列里堆积

`onAppWidgetOptionsChanged` 每次回调都往 `renderExecutor`（单线程，`:192`）投一个完整渲染任务。桌面拖拽缩放手柄会连续触发十几次 `onAppWidgetOptionsChanged`，而一次全尺寸渲染在低端机上是几十毫秒级——**队列来不及消化，用户看到的是"松手后画面还在逐个追"**。

建议加一层 coalescing：按 `appWidgetId` 去重，队列里已有该 ID 的待处理任务就不再重复入队（`ConcurrentHashMap<Int, Boolean>` 或 `LinkedHashSet` 均可）。这是纯性能优化，不改行为。

## 5. 已核查、判定**不是**问题的项

这一节同样是审查结论。以下都是容易误判成缺陷、但实测/细读后确认实现正确的点，列出来避免重复排查：

| 项 | 结论 | 依据 |
|---|---|---|
| 证书固定会不会把用户挡在门外 | **不会，当前完全正确** | 实测线上链：叶子 `CN=www.puretxt.cn`（SAN 含 `puretxt.cn` + `www.`），中间 CA `YR2`，根 `ISRG Root YR`。`network_security_config.xml` 的两个 pin 与中间 CA / 根**逐字节吻合**，且 pin 的是 CA 不是叶子——90 天换证不受影响。还带 `expiration="2027-12-31"` 兜底 |
| 支付宝私钥是否泄进仓库 | **没有** | `git log --all -- lkl-pay-server/certs keystore` 为空；`.gitignore` 与 `lkl-pay-server/.gitignore:36` 双重覆盖 |
| 系统栏适配（targetSdk 35 强制 edge-to-edge） | **正确** | `MainScreenBackground.kt:157-165` 用 `Scaffold { innerPadding -> Column.padding(innerPadding) }` 消费安全区，而 hero 图故意画在 Scaffold 外以铺满状态栏——这正是官方推荐写法，不是漏了 `statusBarsPadding` |
| 删除分类会不会静默删光金句 | **有二次确认且文案明示** | `CategoryManagerDialogs.kt:268`「这将同时清空该目录下的所有诗词金句，此操作不可恢复」 |
| SQL 注入 | **无** | 全部查询走 `?` 占位符 + `arrayOf`；唯二的字符串拼接是 `INSERT ... SELECT` 的固定 SQL |
| 明文 HTTP | **全站禁止** | `base-config cleartextTrafficPermitted="false"`，仅 `debug-overrides` 放行本地联调 |
| 公告广播被第三方伪造 | **已防** | `ReminderWidgetProvider.onReceive` 对自定义 action 先与本应用实际登记的 widgetId 求交集（`:28-39`），再限制单次 64 个 ID |
| 支付回调能否被伪造 | **不能** | 先 `rsaCheckV1` 验签，再校验 `app_id == props.appId`，最后核对金额（`PayOrderService.kt:69-84`，金额解析失败直接拒绝，没有"跳过核对"的分支） |
| 重复通知会不会重复发货 | **不会** | `markPaidIfCreated` 条件 UPDATE + `affected == 0` 时回查终态（`PayOrderService.kt:90-103`），并发由 `PaymentConcurrencyTest` 覆盖 |
| 口令存储 | **达标** | PBKDF2-HMAC-SHA256 / 210k 迭代 / 16 字节盐 / `MessageDigest.isEqual` 恒定时间比较；账号不存在时也跑一次哈希抹平时间差（`UserService.kt:70`） |
| 客户端返回 9000 能不能直接当成功 | **不能，且代码没这么干** | `AlipayPay.kt:12-14` 明确注释 9000 只代表收银台确认，真正放行要 `confirmPaid()` 轮询服务端查单 |
| 令牌过期/换号竞态 | **已处理** | `AccountStore.updateAccountIfTokenMatches` / `clearIfTokenMatches`（`:71-88`）把「校验令牌」与「写库」放进同一临界区 |
| 用户内容会不会上传 | **不会** | 全程本地 SQLite/prefs；`AndroidManifest` 仅 `INTERNET`，无存储/相册权限，选图走系统选择器 `openInputStream(uri)` |

## 6. 架构评价

### 分层的实际形态

```
ui (≈50 文件)  ──直接调用──▶  data/DbHelper（SQLiteOpenHelper 单例）
     │                          data/AppPrefs、WidgetStyle（JSON 序列化）
     ├──▶  render (15 文件)  ◀── WidgetCanvasRenderer（位图 + 两级缓存）
     ├──▶  pay (3)  ──▶ net/ServerClient ──▶ https://puretxt.cn
     └──▶  account (5) ──▶ net/ServerClient
```

**做得好的部分**：

- `render/` 的拆分是真有章法的。`WidgetRenderPipeline` 把绘制固定切成 7 个阶段（底色 → 背景图 → 家族装饰 → 纹理描边 → 正文 → 顶层叠加），形状差异收敛到 `RenderScene` + `ShapeTraits`，42 款风格共用一条管线而不是 42 个 if。这是从"一个 3600 行的 Renderer"重构出来的结果（commit `4946a38`），方向正确。
- `pay/` + `account/` 的契约意识很强。每个文件顶部都写清了"谁负责什么、失败怎么处理、为什么不能简化"，`ProPurchase` 甚至把「激活与消费之间不留挂起点」这种细节写进了注释并落实到了代码顺序（先 `activate` 再 `removePendingOrder`）。
- `WidgetStyle` 的反序列化是防御式写法：单字段非法只降级该字段（`safeEnum`）、旧枚举名有映射表（`SERIF → SOURCE_HAN_SERIF`）、`presetId` 缺失时走字段匹配兜底。

**主要的架构欠缺**（按影响排序）：

1. **无 ViewModel / 无 Repository**。UI 直接持有 `DbHelper`，业务规则（付费判定、PRO 撤销、订单找回）散落在 Composable 的 `LaunchedEffect` 里。表现就是 P2-2 的 758 行。
2. **`WidgetStyle.kt` 是数据模型 + 商品目录 + 序列化 + 付费判定的四合一**（1,494 行）。其中 42 条 `PRESETS` 占了绝大部分，属于"数据"而非"逻辑"，建议拆到 `WidgetPresets.kt`，让 `WidgetStyle` 回到 300 行以内。
3. **跨端契约靠注释维持**。App 与 Server 之间没有共享的 schema，价格（P1-4）、错误码（`RATE_LIMITED`）、响应字段全靠两边手写对齐。当前是对的，但没有机制防止下一次改错。

### 测试体系（这是本项目最被低估的资产）

- 43 个测试类 / 239 用例 / 6,435 行，**无 `@Ignore`**，700+ 条断言。
- `WidgetRenderBaselineTest` 用 Robolectric + `GraphicsMode.NATIVE`（真实 Skia）给 42 款风格出像素指纹，基线入库（150 行 TSV）。这是"改绘制代码必须证明像素没变"的硬约束——**正是它让 42 款风格的渲染重构成为可能**。
- 有 `PaymentConcurrencyTest`（服务端并发重复通知）、`WidgetBitmapBudgetTest`（位图内存预算）、`WidgetProviderIsolationTest`（广播伪造隔离）这类"针对真实事故场景"的测试，不是凑覆盖率。
- 欠缺：无 CI（P2-1）、`androidTest/` 为空（真机行为靠 Robolectric 模拟）、无跨端契约测试。
