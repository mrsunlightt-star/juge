## 三、P0：阻断上线

### P0-1 生产环境 `/api/*` 全部 404，支付与找回 100% 不可用

```
$ curl -s -o /dev/null -w '%{http_code}' -X POST https://puretxt.cn/api/alipay/create
404
```
实测响应体是 **nginx 默认 404 页**，与随机路径 `/api/nonexistent-xyz` 逐字节同形 → 请求**根本没到 Spring**，是反代层没有规则，不是应用层返回。

证据链：
- 客户端 `app/src/main/java/com/juge/app/net/ServerClient.kt:22` `val baseUrl: String = "https://puretxt.cn"`
- 服务端 `lkl-pay-server/src/main/resources/application.yml:18` `port: 8081`，`notify-url: https://puretxt.cn/api/alipay/notify`
- 仓库内 **无任何 nginx 配置文件**（`grep -r proxy_pass` 只命中审查文档本身）

**根因在仓库之外**：服务器上 nginx 没有把 `/api/` 转给 `127.0.0.1:8081`。这同时意味着支付宝的异步通知**全部丢失**——`notify-url` 指向的地址返回 404，支付宝会按官方节奏重投 25 小时后放弃，而重投期间用户已经付了钱。

**修复**（服务器侧，非代码）：
```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8081;
    proxy_set_header X-Forwarded-For $remote_addr;   # 注意：$remote_addr 是覆写
    proxy_set_header X-Real-IP       $remote_addr;
    proxy_read_timeout 60s;
}
```

同一份索引逻辑在 `MainAppScreen.kt:272` 写的是 **`appWidgetIds[page.coerceIn(0, appWidgetIds.size - 1)]`**——一处防了，一处没防。

**实测复现**：我写了一个形态完全镜像该模式的最小 harness（父层捕获 `IntArray` 快照 + `pageCount` 实时读 state + 数组 1→3 后翻到第 2 页），**连续 3 次运行全部复现**：
```
PROBE render page=0 id=11 captured=1 live=1
PROBE ERROR page=2 captured=1 live=3 ArrayIndexOutOfBoundsException
java.lang.ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 1
```
机制：`pageCount` 的 lambda 在**测量阶段**读实时值（已变 3），而 content lambda 来自**上一帧的组合**（数组还是 1 个元素）→ pager 认为第 2 页合法并去组合它 → 用旧数组取下标 → 崩。

真机触发路径：桌面新增组件 → `ON_RESUME` 把 `appWidgetIdsState` 从 1 个更新为 2~3 个 → 同一帧内 pager 发生滚动/布局（用户滑动惯性、`animateToPageOnUserInput`、或 `:235` 的 `animateScrollToPage(index)`）→ 命中窗口。

修法：
```kotlin
val pageWidgetId = appWidgetIds.getOrNull(page) ?: -1
```
并把 content lambda 的数组源与 `pageCount` 统一为同一个实时来源。

### P0-5 订单过期时间依赖 JVM 默认时区，UTC 主机上订单"一出生就过期"

`lkl-pay-server/src/main/kotlin/com/juge/lklpay/service/AlipayPayService.kt:69`
```kotlin
this.timeExpire = LocalDateTime.now().plusMinutes(props.orderExpireMinutes).format(DT)
```
`:170`
```kotlin
private val DT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")
```
全仓 `grep -r "ZoneId\|Asia/Shanghai\|spring.jackson.time-zone"` → **0 命中**。

支付宝按**北京时间**解析 `time_expire`。服务器若是 UTC（云主机默认镜像常见），`LocalDateTime.now()` 得到 UTC 时间，格式化后当作北京时间发出去 → 实际过期时间是"过去 8 小时" → 用户拉到收银台即提示交易已关闭。

修法：`LocalDateTime.now(ZoneId.of("Asia/Shanghai"))`，并在 `application.yml` 显式设置 `spring.jackson.time-zone`。同时 `genOutTradeNo()`（`:159`）也用了 `LocalDateTime.now()`，同样受影响（订单号前缀错 8 小时，不影响唯一性但影响人工排查）。

**P1-12 渲染缓存注释直接撒谎**
`app/src/main/java/com/juge/app/WidgetCanvasRenderer.kt:131-134`
```kotlin
private val thumbnailCache = object : android.util.LruCache<String, Bitmap>(32 * 1024 * 1024) {
    override fun sizeOf(key: String, value: Bitmap): Int = value.byteCount
}   // 只覆写 sizeOf
```
`:235-237` 注释原文：
> 之所以敢直接给原图，是因为本缓存**关闭了 LruCache 的条目回收**（entryRemoved=false，见 thumbnailCache 定义）：条目只增不减、不会被淘汰，原图一旦创建就一直在，调用方持有的引用始终有效

**没有覆写 `entryRemoved`，也没有任何 remove/recycle 逻辑。** 这不是"注释略有出入"，而是**把一条不存在的安全前提当作论证，去支撑"可以不 copy 直接返回原图"这个决定**。一旦真的发生淘汰（用户自定义背景图数量上去），会出现"已回收位图被绘制"或内存双持。

### 资源与渲染性能（低端机会真实兑现）

这一组不是"理论上的优雅问题"。目标机型是千元安卓 + 桌面常驻组件，`renderExecutor` 是**单线程 daemon**，OOM 直接打死进程——而项目没有任何崩溃上报能告诉你发生了什么（见 P2-3）。

排序说明：**P1-18 与 P1-19 在低端机上等价于 P0**（确定性 OOM 崩溃 + 无观测手段）。之所以没放进第三节，是因为它们不像 P0-1~P0-5 那样 100% 必现，而是取决于照片尺寸、预设组合与机型堆上限。修的时候请按 P0 对待。

**P1-18 裁剪大图峰值 24~32MB：采样上限与目标尺寸完全脱钩**
`app/src/main/java/com/juge/app/CropImageHelper.kt:48-50`
```kotlin

private const val DEFAULT_CROP_WIDTH = 840        // 实际只输出 840×270
private const val DEFAULT_CROP_HEIGHT = 270
```

`:154-156` 按 `MAX_IMAGE_DIMENSION` 逐次 ×2 采样；`:191-195` EXIF 旋转用 `Bitmap.createBitmap(bitmap, 0, 0, w, h, transform, true)`。

一张 4000×3000 的手机照片采样到 **2048×1536 ≈ 12MB**，旋转时源图 + 旋转图同时驻留 = **24MB 峰值**；再叠加 `presetImageCache`（24MB）与 `thumbnailCache`（32MB），总计 **80MB+** —— 已经接近中低端机 `largeHeap` 之外的常规堆上限（多为 192~256MB），而此时用户什么都没做，只是选了一张背景图。而最终产物只有 840×270 = **0.9MB**，中间多花了 26 倍内存。

修法：把采样上限改成按 `targetWidth/targetHeight` 反算（`inSampleSize` 直接取"能覆盖目标框的最小 2 的幂"），旋转用 `Matrix` 合进一次绘制而不是再分配一张全尺寸位图。

同一函数还有个小的连带缺陷：`:246-278` 的 `cropAndSaveBitmap` 里 `val croppedBitmap = Bitmap.createBitmap(...)`（`:258`）在**正常路径** `:275` 有 `croppedBitmap.recycle()`，但 `:278` 的 `catch (e: Exception)` 分支**没有回收**——压缩/写盘抛错时那张 840×270 的位图泄漏。量不大（0.9MB），但和上面的峰值叠加在同一个用户动作里。

`app/src/main/java/com/juge/app/ReminderWidgetProvider.kt` 的 `onUpdate:46-56`、`onAppWidgetOptionsChanged:59-68`、`dispatchAsync:162` 三处都是 `catch (e: Exception)`；`app/src/main/java/com/juge/app/WidgetCanvasRenderer.kt:99-116`

## 六、做得好的地方（客观记录，不是客套）

审查必须两边都报，否则不叫客观。以下每一条都经过代码验证：

**1. 钱的正确性是全项目最高水准**
`PayOrderService.kt:62-110` 的 `markPaid` 顺序是：查单 → **核金额** → 幂等判断 → CAS 更新。注释明确写着"已付款也必须核对本次结果的金额，不能让幂等分支绕过查询的校验闸门"——这个顺序是对的，而大多数人会先判幂等。

`PayOrderRepository.kt` 用条件 UPDATE（`WHERE o.status = :created`）+ `@Modifying(clearAutomatically = true, flushAutomatically = true)` 做 CAS，而不是"读-改-写"。

`PaymentConcurrencyTest.kt`（199 行）是**真并发测试**：真线程池 + 真实事务 + H2 内存库，用双 `CountDownLatch` 卡在 CAS 内部制造竞争，`Pause.stopHere()` 里还断言 `TransactionSynchronizationManager.isActualTransactionActive()` 确保真在事务里。覆盖了「4 线程重复通知只 1 个成功」「闭单先提交 → 付款失败且 paidAt 为 null」「闭单持旧快照不覆盖已付款」。**这组测试是"钱不会被并发写坏"的实际证据，不是装饰。**

**2. 反序列化的失败模式选对了**
`WidgetStyle.fromJsonString`（`:324`）用 `safeEnum`：
```kotlin
try { enumValueOf<T>(name) } catch (e: IllegalArgumentException) { fallback }
```
未知枚举值**静默回落而不是崩**。配合 `proguard-rules.pro` 里 keep `values()/valueOf()` 并注释说明「R8 enum unboxing 会把 name() 压成 int，桌面上已保存的样式会全部读不回来」——这是**踩过坑并写进规则**，不是抄模板。

**3. 密钥卫生干净**
- `keystore.properties`、`keystore/`、`lkl-pay-server/certs/`、`data/` 全在 `.gitignore`
- `git log --all -- keystore keystore.properties lkl-pay-server/certs` **为空**
- 全历史扫私钥/密码正则（`BEGIN PRIVATE KEY`、`MIIE...`、`storePassword=`）**0 命中**
- `certs/alipay_app_private_key.txt` 权限 **600**

对个人项目而言这是很少见的克制。

**4. TLS pin 钉得专业**
钉的是**中间 CA + 根**（`nWN7PSep5XDQdge5zK24CnCRXHr3KvzhKEGxsdqCX9E=` / `fk6IOKit1ild5647BH06ujSIq5XbCgqlbYl6ANhhi88=`），不是叶子证书——Let's Encrypt 90 天换证不会打断；并且写了 `pin-set expiration="2027-12-31"`，到期自动回落而不是把用户锁死在外面。我拉了实时证书链逐张算 SPKI，**两个 pin 与线上逐字节一致**。

**5. 数据层没有注入面**
`DbHelper.kt` 全部 `rawQuery(..., arrayOf(id.toString()))` 参数化；4 处事务成对 `beginTransaction`/`setTransactionSuccessful`/`endTransaction`；`onDowngrade` 幂等补建全部表保留数据（而不是 `DROP`）。这在"个人项目"里是罕见的严谨。

**6. 一些设计把产品直觉写成了可执行规则**
`WidgetStyle.kt:1336` 的 `SHAPES_WITHOUT_BACKGROUND_COLOR` 列了 15 个形状，每个都写了"为什么这个形状不能铺底色"（框外透明会露色块），唯一入口 `supportsBackgroundColor(shape)`。
`AppPrefs.kt:22` 把隐私同意做成 `CURRENT_PRIVACY_VERSION = "2026-10-01"` —— 政策改版只改一个常量就能重新征得同意。

**7. 并发与生命周期处理有几处很到位**
- `ReminderWidgetProvider.dispatchAsync`：`goAsync()` + `AtomicBoolean finishOnce` + 超时兜底，不会因为渲染卡死让系统杀掉广播
- 单线程 `widget-render` daemon executor，注释说明动机是"避免并发解码位图导致内存峰值过高"
- `onReceive` 对 `ACTION_MIUI_UPDATE` 做**不信任广播内 ID** 的白名单过滤（`requested.filter { it in owned }.take(64)`）
- `WidgetBitmapBudgetTest` 用 `preview.sameAs(desktop)` 逐像素断言小尺寸桌面位图与预览一致

**8. 测试总量与形态都超标**
239 个用例、48 个文件，`0 失败`。有渲染指纹基线（8×4 网格平均色 + 不透明像素占比）、UI 语义基线、手势状态审计、以及那个诚实的注释——"第四個场景是补上来的：首屏只拍得到两行，明信片行在视口之下，于是它的行标题被整行删掉，几周都没人发现"。

**9. 注释记的是"为什么"，不是"是什么"**
全仓 `TODO/FIXME/XXX/HACK` **0 条**，而注释里写满了决策记录与反例。这在同类项目里极罕见，也是这份代码可维护性的主要来源。

## 九、一句话结语

这个项目的**下限很高**——金额校验、并发状态机、密钥卫生、渲染基线、注释质量都超出了它应有的水平，说明写它的人清楚"什么是要命的地方"。问题在于**上限没接上**：一个真正的上线流程会强制回答"反代配了吗""pid 填了吗""官网文案改了吗""版本号多少"——这四个问题的答案现在都是"没有"。

技术上它离能上线只差**几小时的工作量**；流程上它缺的是一道**上线前必须过的清单**。

再补一句关于"深度"的：这个项目在**难的地方做对了**（金额闸门顺序、CAS 幂等、TLS pin 层级、safeEnum 降级、密钥卫生），在**烦的地方漏了**（反代、pid、隐私口径、版本号）。而资源管理这一层（P1-18~26）是唯一"既不难也不烦，只是没人回头看"的部分——它恰好落在最容易被忽略的位置：低端机上不会报错，只会安静地 OOM，而项目连崩溃上报都没开。
