#### 8. 会员判定加固：从「本地算得出来」到「服务端签得出来」（P1-3）

这是本轮最大的一处新增。原实现（`TrialManager` v2）的判定是
「签名哈希 → 三键一致 → checksum」，三步都在本机可复算 —— 反编译拿到签名证书、
照抄 `computeChecksum` 的算法，手工写六个键就是永久 PRO。
`TrialManagerTest` 早先的注释也自认「对 1.99 元买断产品，那是有意接受的防盗水位」。

现在的链路：

**服务端签发** `lkl-pay-server/src/main/kotlin/com/juge/lklpay/service/EntitlementSigner.kt`（149 行）

- 凭证格式 `v1.<base64url(payload JSON)>.<base64url(RS256 签名)>`，`SIGN_ALGORITHM = "SHA256withRSA"`；
- payload 字段顺序固定：`{"v":1,"productId":…,"buyerHash":sha256Hex(buyerUserId),"paidAt":…,"issuedAt":…,"nonce":…}`；
- `nonce` 来自 `SecureRandom().generateSeed(12)`，**不做重放防护**，只为日志对账；
- 私钥 `by lazy` 加载，`ready` 失败时只 `log.error`，不拖垮启动；
- `publicKeyFingerprint()` 供启动自检与测试比对。

**客户端验签** `app/src/main/java/com/juge/app/data/EntitlementVerifier.kt`（144 行）

- `verify(credential: String?, publicKeyPem = testPublicKeyOverride ?: BUILTIN_PUBLIC_KEY_PEM): Entitlement?`（`:82`）；
- 三段式拆分 → 补 `=` 到 4 的倍数 → `Base64.URL_SAFE or Base64.NO_WRAP` 解码 →
  验签 → 解析 JSON → `takeIf { it.productId == PRODUCT_ID }`（`PRODUCT_ID = "pro_permanent"`，`:57`）；
- `internal var testPublicKeyOverride` 是测试 seam，注释写明「把生产私钥拷进
  `test/resources` 才是真的把私钥入库」。

KDOC 里写清了边界：验签只回答「这段声明是不是服务端签的」，不回答「这台设备有没有付过钱」；
凭证可被同一用户复制到第二台设备（产品定位是换机找回，不做设备绑定）；
换公钥等于已发凭证全废。

**判定升级为 v3** `app/src/main/java/com/juge/app/data/TrialManager.kt`

`isActivated()`（`:71`）五步，任一环不成立即 false：

1. APK 签名与首次锁定值一致；
2. 三个布尔键一致；
3. checksum 匹配；
4. **开发开关只在 debug 包放行**；
5. **存在一份验签通过的权益凭证**。

前三步本地可复算，只能提高篡改成本；真正不可伪造的是第 5 步。第 5 步不成立时
**只返回 false、不清库** —— 清库会让「用户其实买过、只是数据迁移出问题」
变成不可诊断的静默降级。

新增两个方法：

- `activateWithEntitlement(credential, payMethod = PAY_METHOD_RECOVER, activatedAt = 0L)`（`:134`）：
  先验签，失败直接 `return false` 不落盘；`shownAt` 依次取 `activatedAt > 0` →
  `entitlement.paidAt > 0` → 当前时间；
- `activateDebug()`（`:169`）：`if (!BuildConfig.DEBUG) { Timber.w(...); return false }`。
  与前者分开命名，是为了让「不带凭证也能激活」这件事在调用点就一目了然。
  调用点 `app/src/main/java/com/juge/app/ui/main/MainTopBar.kt:327` 由
  `activate(PAY_METHOD_DEV)` 改为 `activateDebug()`。

**服务端签发点** `lkl-pay-server/src/main/kotlin/com/juge/lklpay/web/AlipayController.kt:140`

```kotlin

fun findPaidByBuyer(buyerUserId: String): List<PayOrder> {
    val expectedFen = payProperties.products[PRODUCT_ID]?.amountFen
    return orders.findByBuyerUserId(buyerUserId).filter { order ->
        order.status == PayOrder.STATUS_PAID &&
            order.productId == PRODUCT_ID &&
```

#### 18. 限流判定在锁外 + XFF 可取伪造值（P1-13 / P1-14）

**修复**：自增与比较搬进**同一个 `compute` lambda**，用
`val decision = intArrayOf(0, 0)`（`[0]`=本窗口次数、`[1]`=是否放行）带出结果。

（超 `MAX_BUCKETS` 整表 `clear()` 并 WARN），防止 bucket 表被 IP 段扫爆。

**问题二（XFF 伪造）**：原 `clientIp()` 取 XFF **最左**值。`$proxy_add_x_forwarded_for`
是追加语义，最左值由客户端控制 —— 换一个 header 就换一个限流桶。

**修复**（`lkl-pay-server/src/main/kotlin/com/juge/lklpay/web/AlipayController.kt:190-208`）：

```kotlin
private fun clientIp(request: HttpServletRequest): String? {
    val direct = request.remoteAddr?.takeIf { it.isNotBlank() }
    if (direct == null || !isTrustedProxy(direct)) return direct
    request.getHeader("X-Forwarded-For")?.split(",")?.map { it.trim() }
        ?.lastOrNull { it.isNotEmpty() }?.let { return it }
    request.getHeader("X-Real-IP")?.trim()?.takeIf { it.isNotEmpty() }?.let { return it }
    return direct
}
```

只有直连方是本机回环（`127.0.0.1` / `::1` / `127.*`）才信任 XFF，且取**最后一个**值。

**问题三（`/auth-info` 无限流）**：该端点每次调用都要做一次 RSA 签名，是现成的
CPU 放大点。现在五个端点全部限流：`create`(`:58`)、`query`(`:101`)、`notify`(`:230`)、
`auth-info`(`:376`)、`recover`(`:418`)，门控顺序统一为 **配置检查 → 限流 → 干活**。
新增 `AUTH_INFO` 限额 10 次/分钟/IP。

#### 23. OOM 穿透到 daemon 线程（P1-19）

  `try { …七段绘制… } catch (t: Throwable) { 先回收半成品再抛出 }` ——

## 二、复核后撤回或更正的判断

### 1. 「TLS pin 与线上不一致 / 全站 TLS 中断」——**判断有误，已撤回**

审查中一度认为 `network_security_config.xml` 的 pin 与线上证书链不匹配。复核后：
pin 的是**中间 CA `YR2`** 的 SPKI `nWN7PSep5XDQdge5zK24CnCRXHr3KvzhKEGxsdqCX9E=` 与
**根 `ISRG Root YR`** 的 SPKI `fk6IOKit1ild5647BH06ujSIq5XbCgqlbYl6ANhhi88=`，
与线上证书链**逐字节一致**；叶子 `CN=www.puretxt.cn` 刻意未 pin（90 天一续期）。

误判的真实原因：拿本机 154 张系统根证书去找 `YR2` 这个名字找不到（它是中间 CA，
不在信任库里）。**原判断作废，配置正确，未做改动。**

### 2. `LineBreaker.JUSTIFICATION_MODE_INTER_WORD` 的 `NoSuchMethodError` 风险——**降级**

查 `api-versions.xml`：`StaticLayout$Builder.setJustificationMode(int)` since = 26，
常量值为 1 且编译期内联，`SDK_INT >= O` 的守卫本身正确 →
**不是崩溃风险**，仅 lint `InlinedApi` 规范性告警。未改代码。

### 3. 「`http://puretxt.cn:8081` 可达」——**结论不可靠，已删除**

`curl -sv` 显示该域名解析到 `198.18.2.66`（Clash 类代理的 fake-ip 保留段），
本机网络环境下这个结论测不出来。只有 `443` 上 `/api/*` = nginx 404 这一条是稳的，
P0-1 的判断仍成立。另外新增 `server.address: 127.0.0.1` 之后，
即便公网可达，服务本身也不再监听外部网卡。

### 4. 「UI 直连 `DbHelper` 29 处」——**数字更正为 25 处**

实测 `grep -c` 分布：`ui/main/LibraryPane.kt` 17 处、`ui/main/MainAppScreen.kt` 6 处、
`ui/main/MainTopBar.kt` 3 处、`ReminderWidgetProvider.kt` 3 处、`CropImageHelper.kt` 1 处
（后两者不在 UI 层）。29 是早先粗算，以 25 为准。

### 5. 「`getWidgetDeclaredSizeDp` 是死代码」——**判断有误，保留**

它确实只有测试调用，但测试类注释写明「App 内预览已不再按它出图（2026-10-08 起改按
风格的最佳显示尺寸）……这份映射现由回归测试与后续『按入口提示尺寸』类功能取用」。
它是「入口 → 声明尺寸」的唯一权威映射，已有 6 条回归测试锁定
（紧凑入口 250×110 / 主入口 250×250 / 不随桌面拉伸变化 / 无组件时 4×2 兜底 /
问不到归属时按实时行数兜底 / 250dp→4 行 110dp→2 行）。删掉会让
「4×4 入口被拉成 4×2」重新变成靠肉眼发现的问题。**保留**。

## 三、仍未处理（明确记录）

| 项 | 原因 |
| --- | --- |
| **生产 nginx 反代未生效**（P0-1） | 仓库里从来没有反代规则，已产出 `deploy/nginx-juge-api.conf`，**需要服务器侧 include 才生效**。本机无法验证线上配置。 |

| **UI 直连 `DbHelper` 25 处未抽 repository**（P2-14） | `DbHelper` 是单例但**显式传参**（非 Service Locator）；`LibraryPane.kt:50-60` 的 `launchLibraryChange` 已在 `Dispatchers.IO` 上跑，且正确 rethrow `CancellationException`。抽 repository 需要重写 25 个调用点 + 6 个测试的构造参数，收益是可测性与分层，代价是一大坨纯搬运。而真正的缺陷（`check()` 失败被 catch 成 Toast）不在分层上，在错误类型上。 |
| **140 条 `UseKtx` 等 lint 建议**（P2-2） | 属建议级（`androidx.core` 扩展函数替换），不影响正确性。逐条改会产生一个巨大的、与审查无关的 diff。 |
| **`RenderFingerprint` hash 零容差 / `UiFingerprint` 只收屏内节点**（P2-17/18） | 两项都是**有意的基线策略**：前者靠严格 hash 守住 P1-21 的 `Picture` 重放必须逐像素等价；后者注释与实际行为一致。已通过 CI 的 `-PciSkipPixelBaselines` 解决「换机器假红」，不在本地放宽判据。 |
| **`seller_id` 未校验**（P0-5 顺带） | 支付宝公钥验签 + `app_id` 校验已足够防伪；`seller_id` 属加固冗余。已在验签失败日志里输出 `sellerId` 便于排查。 |
| **真机回归** | 本轮全部验证是 Robolectric + JVM 单测 + APK 静态核验（`aapt2 dump badging/permissions`）。裁剪的 EXIF 8 种 orientation、桌面组件的实际拉伸表现、支付宝真付流程，都需要真机。 |
